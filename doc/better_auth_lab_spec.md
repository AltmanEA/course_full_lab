# Лабораторные работы — Better Auth (Next.js + tRPC + Drizzle + PostgreSQL)

Документ определяет правила разработки и тестирования лабораторных задач
по интеграции Better Auth в fullstack-архитектуру.

Документ основан на:

- Универсальной спецификации лабораторных задач (spec_lab)
- Архитектурной модели курса Better Auth
- DI-подходе и слоистой архитектуре

Документ является технологически конкретным (Better Auth),
но сохраняет универсальные методические принципы spec_lab.

---

# 1. Архитектурная модель курса

Все задачи разрабатываются в рамках следующей архитектуры:

UI  
↓  
tRPC (router)  
↓  
Access layer  
↓  
Drizzle ORM  
↓  
PostgreSQL  

Better Auth является инфраструктурным cross-cutting слоем,
который:

- выполняет аутентификацию,
- управляет session,
- передаёт user через context,
- не содержит бизнес-логики.

Auth не является частью UI или router.
Он интегрируется через DI.

---

# 2. Общие принципы лабораторных по Better Auth

## 2.1. Auth как инфраструктура

Задачи не должны:

- сводиться к конфигурации библиотеки,
- превращаться в UI-задачи,
- смешивать бизнес-логику и проверку доступа,
- использовать глобальные auth-импорты в бизнес-коде.

Каждая задача должна закреплять архитектурный аспект auth.

---

## 2.2. Progression rule

Каждая лабораторная:

- вводит ровно одно новое действие или концепцию,
- не объединяет несколько новых механизмов,
- логически продолжает предыдущую.

Примеры допустимых новых действий:

- получение session,
- protectedProcedure,
- RBAC,
- ownership,
- cookie security,
- expiration,
- CSRF,
- access-layer проверка.

Недопустимо:

- объединять RBAC и ownership в одной задаче,
- одновременно вводить router и access-layer защиту,
- совмещать cookie security и CSRF.

---

## 2.3. Размер решения

Решение:

- 2–10 строк осмысленного кода,
- минимум два логических действия (кроме вводных задач),
- не должно быть простым прокидыванием вызова.

---

# 3. Структура лабораторной задачи

Каждая задача включает:

- README.md
- bauthXX.ts (или routerXX.ts / accessXX.ts)
- bauthXX.spec.ts

---

## 3.1. README.md

README должен содержать:

- цель задачи,
- тип задачи (infrastructure / router / access / security),
- формулировку,
- ограничения,
- проверяемые требования.

README не должен:

- описывать тестирование,
- раскрывать внутреннюю механику Better Auth,
- содержать код решения,
- ссылаться на предыдущие задачи.

---

# 4. Требования к тестированию

## 4.1. Главный принцип

Тестируется интеграция и архитектура.
Better Auth как библиотека не тестируется.

Тестируется:

- корректная передача user,
- корректная обработка ошибок,
- изоляция слоёв,
- правильная работа DI,
- корректная security-конфигурация.

---

## 4.2. Запреты

Тестам запрещено:

- выполнять реальные HTTP-запросы,
- использовать реальный браузер,
- зависеть от Next.js runtime,
- использовать реальные cookie из браузера,
- проверять исходный код через анализ текста,
- использовать spy на ESM-экспорт для проверки структуры.

---

## 4.3. DI обязателен

Запрещено:

- импортировать auth напрямую в router,
- использовать глобальный currentUser,
- вызывать getSession внутри бизнес-функции.

Разрешено:

- передавать user через context,
- передавать authService через DI,
- мокать зависимости в тестах.

Тесты должны подтверждать,
что логика зависит только от injected данных.

---

# 5. Проверка уровней защиты

Задачи разделяются по уровням:

1. Session-level
2. Router-level
3. Access-layer
4. UI-level

Нельзя смешивать уровни в одной задаче.

---

# 6. Проверка protectedProcedure

Тест должен проверять:

1. ctx.user = null → выбрасывается UNAUTHORIZED
2. ctx.user существует → процедура выполняется

Проверяется:

- тип ошибки,
- факт выброса,
- корректный результат.

Не проверяется:

- внутренний вызов middleware,
- текст сообщения ошибки.

---

# 7. Проверка RBAC

Обязательные сценарии:

1. Нет пользователя → UNAUTHORIZED
2. USER → FORBIDDEN
3. ADMIN → успех

Недопустимо:

- проверять роль через анализ исходного кода,
- проверять порядок middleware через spy.

---

# 8. Проверка ownership

Обязательные сценарии:

1. Нет пользователя → UNAUTHORIZED
2. user.id !== ownerId → FORBIDDEN
3. user.id === ownerId → успех

Ownership должен быть реализован
в указанном в задаче слое (router или access).

---

# 9. Session lifecycle

Если задача связана с session:

Тест должен проверять:

- создание session,
- истечение,
- инвалидацию,
- rotation (если требуется).

Тест не должен:

- зависеть от реального времени,
- использовать Date.now без фиксации,
- зависеть от порядка выполнения.

Рекомендуется:

- использовать injected clock,
- мокать storage.

---

# 10. Cookie security

Если задача связана с cookie:

Проверяется конфигурационный объект:

- HttpOnly = true
- Secure = true (production)
- SameSite корректный
- expiration установлен

Не используется браузерная среда.

---

# 11. CSRF

Если задача вводит CSRF:

Проверяется:

- наличие токена,
- совпадение токена,
- отклонение запроса при несовпадении.

CSRF не должен смешиваться
с cookie-конфигурацией в одной задаче.

---

# 12. Ошибки авторизации

Должны различаться:

- UNAUTHORIZED — нет пользователя
- FORBIDDEN — недостаточно прав
- NOT_FOUND — доменная ошибка
- INTERNAL_SERVER_ERROR — инфраструктура

Тесты должны проверять именно тип ошибки,
а не текст сообщения.

---

# 13. Работа с состоянием

Если используется:

- in-memory session store,
- singleton authService,
- module-level cache,

тест обязан:

- сбрасывать состояние,
- изолировать модули,
- не зависеть от порядка выполнения.

---

# 14. Архитектурные запреты

Недопустимо:

- проверять роль только в UI,
- выполнять бизнес-логику в router,
- обращаться к DB напрямую из процедуры,
- импортировать auth глобально,
- дублировать проверку в нескольких слоях без причины.

---

# 15. Критерии качества лабораторной

Задача считается корректной, если:

- невозможно пройти тесты без реальной проверки прав,
- используется DI,
- проверяются все ветви доступа,
- отсутствуют скрытые зависимости,
- соблюден progression rule,
- соблюдено разделение ответственности.

---

# 16. Требования к именованию

Нумерация задач:

bauth01  
bauth02  
…  
bauth40  

Каждая задача автономна.

Задачи не должны зависеть
от состояния предыдущих лабораторных.

---

# 17. Итоговый принцип

Лабораторные по Better Auth должны формировать
production-ориентированную архитектурную модель:

- Auth как инфраструктурный слой
- DI как обязательный механизм интеграции
- Разделение router / access
- Корректная модель ошибок
- Production-ready session security
- Устойчивость к типовым атакам

Если задача можно пройти,
не реализовав реальную проверку доступа —
она считается некорректной.

# 18 Дополнительные замечания 

1. Type-only задачи непроверяемы без runtime-якоря
Если лабораторная вводит только TypeScript-типы, тесты могут проходить без реализации.
Нужен runtime-артефакт или поведенческая проверка.

2. instanceof ломается при дублировании классов между задачами
Автономность задач требует локальных классов ошибок.
Импорт классов из других задач приводит к падению instanceof.

3. Моки и module-state требуют обязательной очистки
Даже без явного singleton тесты могут зависеть от состояния mock-функций.
clearAllMocks() становится обязательным шаблоном.

4. Автономность задач конфликтует с архитектурной композиционностью
Переиспользование предыдущих реализаций (например, adminProcedure) нарушает изоляцию.
Нужно проектировать задачи так, чтобы они были логически связаны, но файлово независимы.

5. Тесты должны проверять архитектуру, а не просто поведение
Важно проверять тип ошибки, порядок вызовов и DI-модель.
Иначе студент может пройти задачу с архитектурно неправильным решением.
